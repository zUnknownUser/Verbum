# backend/ — the Verbum API (Go)

Google Cloud reading audio: `POST /v1/tts` (MP3, pt-BR/en-US). Configuration, sample requests,
validation and App integration handoff: [TTS.md](TTS.md).

Serves [`api/openapi.yaml`](../api/openapi.yaml). Uses `net/http` and PostgreSQL through pgx (the driver already specified by Task 11).
With `VERBUM_DATABASE_URL` it reads PostgreSQL; without it, it reads the explicitly labelled
development fixtures (`db/seed/fixtures.json`). The wire contract is unchanged.

## Run it

```sh
cd backend
go run ./cmd/api                 # http://localhost:8080
curl localhost:8080/v1/entities/fixture.person.david
curl "localhost:8080/v1/daily-verse?days=3"
go test ./...                    # contract tests: responses must equal api/examples/*.json
```

Docker (from the repo root): `docker build -f backend/Dockerfile -t verbum-api . && docker run -p 8080:8080 verbum-api`.

## How it is laid out

```
cmd/api/main.go            wires config → store → HTTP; graceful shutdown. Start reading here.
internal/domain/           the wire types — one struct per schema in openapi.yaml. No logic.
internal/store/store.go    the Store interface: the ONLY way handlers reach content. Read-only.
internal/store/memory/     Store over fixtures.json. Reference implementation; tests use it.
internal/store/postgres/   Read-only SQL queries through pgxpool; no startup fixture cache.
internal/seed/             Atomic fixture import into an empty database.
cmd/seed/                  Explicit development seed command; never called by the API.
internal/testdb/           Isolated schemas for PostgreSQL integration tests.
internal/httpapi/          server.go (routes) · handlers.go (one func per route) · problem.go (errors)
                           contract_test.go proves every api/examples/*.json is answered byte-for-byte.
internal/dailyverse/       the verse-of-the-day pick — same algorithm as the apps (tested on the same dates).
internal/realtime/         brokers OpenAI Realtime ephemeral sessions; optional, needs OPENAI_API_KEY.
internal/embeddings/       embeds one search query at request time; optional, same key, degrades to lexical search.
internal/synthesis/        calls OpenAI chat completions for Ask; optional, same key.
internal/ask/              Task 12 orchestration: retrieval, prompt assembly, citation validation. No network calls of its own.
db/migrations/             Postgres schema (§25/§26/§33), idempotent SQL.
db/seed/fixtures.json      GENERATED by api/scripts/gen-examples.py — do not edit by hand.
```

Rules the code follows (from docs/PRODUCT.md):
- **Never invent.** No content for a chapter → `404 content_unavailable`, not a generated paragraph (§3.5).
- **Every claim is sourced** (§33): relationships, details and datings carry `sourceReferenceIds`.
- **One error shape** (§52): `Problem {code, message}`; handlers map `store.ErrNotFound` → 404,
  everything else → 500 with the detail logged, never sent.
- **Read-only.** Content enters through the editorial pipeline (`pipeline/`, §32), not this API.

## Ask Scripture (`/v1/ask`, Task 12)

`internal/ask.Service.Ask` — hybrid retrieval (the same `Store.SearchPassages` as `/v1/search`)
→ evidence text (`Store.PassageText`) → prompt assembly → `internal/synthesis` (OpenAI chat
completions, JSON mode) → citation validation → response. Never streamed: retrieval always
completes before synthesis starts (§73), and there is no partial-response path.

**The model is never trusted to name a Bible reference.** It only returns small integers
indexing into the evidence list this package already retrieved and confirmed has real stored
text; `validateCitations` drops anything out of range silently. An answer that ends up citing
nothing verifiable is discarded and replaced with the same empty/low-confidence response used
when retrieval finds no evidence at all — never shown as if it were grounded. `entityReferences`
is always `[]` in this increment (see the package doc for why) and `sourceReferences` is built
by this code, not the model, from the translation actually used.

**A guardrail that needed a second, deterministic layer.** §31 requires recommending
professional help on high-stakes (medical/legal/financial/mental-health) questions. Testing on
2026-09-13 found the prompt instruction alone was not reliably followed — a direct "I feel
hopeless and depressed" question got a purely devotional answer, twice, even after strengthening
the wording. `internal/ask/safety.go` now appends a fixed, non-generated note whenever the
*question* (not the model's answer) matches a conservative keyword list, skipping it only if the
model's own answer already covers it. This is documented as a floor under the prompt, not a
replacement for it — the keyword list is not exhaustive, and a real safety review of this
mechanism (not just the two cases tested here) has not been done.

Not implemented in this increment: PT-BR (blocked on the same license gap as search), streaming,
and any evaluation of answer quality/citation precision beyond the manual spot checks above.
`VERBUM_ASK_MODEL` overrides the synthesis model (default `gpt-4o-mini`, same budget-conscious
default as the pipeline's extraction stage) independently of anything else that uses OpenAI.

**Entity linking (2026-09-13):** `entityReferences` names entities whose curated `keyPassages`
cover a passage the model actually cited (`Store.EntitiesForPassages`, `entity_key_passages`) —
never derived from the question text, so it inherits the same fabrication guarantees as passage
citations. Verified with a real question ("how did David defeat Goliath"): correctly linked to
`fixture.person.david`, `fixture.person.goliath` and four related fixture entities. A linking
failure degrades to an empty list, never fails the answer.

**Product-scope note (owner feedback, 2026-09-13, not yet acted on):** the owner does not want
Ask to become a general life-advisor — the professional-help note in `safety.go` should end up
grounded in what the answer itself says, not triggered by matching the question against a
keyword list the way it works today. Revisit with the owner before extending that list further.

## Direct reference search (§28)

`internal/reference.ParseVerse` recognizes "<book> <chapter>:<verse>" (an OSIS id or one common
English name — not the apps' full abbreviation/range parser) in `/v1/search`'s `q`. When it
parses and the verse exists in `scripture_verses`, `passages` is exactly that one verse and
hybrid retrieval (and its embedding call) is skipped entirely — a real "why pay for an API call
you don't need" win, not just a ranking preference. A reference-shaped query that does not exist
in the corpus (typo, wrong verse count) falls through to hybrid search instead of erroring, and
logs a `§54` "failed reference parsing" line either way. Verified with "John 3:16" (exact hit,
no embedding call) and "John 99:99" (falls through to hybrid search, no error).

## Observability (§54, 2026-09-13)

Every log line is now structured (`slog`, JSON by default — `VERBUM_LOG_FORMAT=text` for a
readable local terminal) and every request carries a short id (`internal/reqid`) that its own
handler's latency/failure lines repeat, so `ask: query embedding`, `ask: retrieval`,
`ask: synthesis` and the outer `request` line for the same call can be correlated without a
tracing backend. Also logged: citation-validation drops (`ask: citation validation dropped
out-of-range indexes`) and reference-parse misses (`search: reference parsed but not found`).

This is deliberately **not** OpenTelemetry spans/exporters yet — there is no chosen collector or
vendor to send them to, so wiring one in now would be a real infrastructure dependency nobody
asked for. `internal/reqid`'s doc comment explains the intended migration path once one is
chosen. The TTS chapter cache is documented in [TTS.md](TTS.md); cache hit metrics are not yet exposed.

## PostgreSQL development setup

From `backend/`, with Go 1.24+ and Docker:

```powershell
docker compose -p verbum-backend up -d
$env:VERBUM_DATABASE_URL = 'postgres://verbum:verbum@localhost:5432/verbum?sslmode=disable'
go run ./cmd/seed
go run ./cmd/api
```

Compose applies all migrations on the **first** initialization of its volume. For a database
created before this block, apply the additive migration explicitly before seeding/running:

```powershell
docker compose -p verbum-backend exec -T db psql -U verbum -d verbum -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/0002_content_order.sql
docker compose -p verbum-backend exec -T db psql -U verbum -d verbum -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/0003_editorial_publication.sql
```

`cmd/seed` imports only the existing development fixture file, in one transaction. It requires
empty content tables and rejects repeat execution without overwriting existing content. It does
not approve content, import real sources, or publish AI proposals. Real publication remains the
human-reviewed Python pipeline described in `pipeline/README.md`.

## Database validation

```powershell
$env:VERBUM_TEST_DATABASE_URL = 'postgres://verbum:verbum@localhost:5432/verbum?sslmode=disable'
go test -count=1 ./...
go vet ./...
```

The test URL must be a PostgreSQL URL for a **development** database with schema-creation rights.
Tests create a unique schema, apply migrations twice, load fixtures, and drop only that schema
on cleanup. Application tables are untouched. Without this variable, PostgreSQL tests explicitly
skip; passing only the memory tests does not validate the database store.

On this Windows workspace, Go validation ran in `golang:1.24` containers connected to
`verbum-backend_default`, using PostgreSQL 17. No app tests or builds were run.

After the local database has been migrated and seeded, from the repository root:

```powershell
docker build -f backend/Dockerfile -t verbum-api:local .
docker run -d --name verbum-api-local --network verbum-backend_default -p 127.0.0.1:8080:8080 -e VERBUM_DATABASE_URL=postgres://verbum:verbum@db:5432/verbum?sslmode=disable verbum-api:local
```

The initial seed can also run through Docker from the repository root:

```powershell
docker run --rm --network verbum-backend_default --mount "type=bind,source=$PWD,target=/repo" -w /repo/backend -e VERBUM_DATABASE_URL=postgres://verbum:verbum@db:5432/verbum?sslmode=disable golang:1.24 go run ./cmd/seed
```

The local delivery already has this seed and API container running; do not seed again.
Inspect with `docker logs verbum-api-local`; stop with `docker stop verbum-api-local`,
and resume with `docker start verbum-api-local`. This is a local fixture environment, not a deployment.
The image build and all seven example responses against the running image were verified.

## OpenAI credential

The owner's key is stored outside the repository at
`%LOCALAPPDATA%\Verbum\secrets\openai-key.dpapi`, encrypted with Windows DPAPI for the current
Windows account. Directory access is restricted to that account and SYSTEM. It is not in
source, an environment file, the Docker image, or a container image layer.

For rotation, run `backend/scripts/Set-OpenAIKey.ps1` from the repository root and enter the
new key at its masked prompt. The ciphertext depends on this Windows user's credentials.

Five things now use it, all confirmed working against the real OpenAI API (2026-09-12/13):
`pipeline/extract.py` and `pipeline/verbum_pipeline/scripture.py` (see `pipeline/README.md`;
`pipeline/run.ps1` decrypts the secret transiently for their commands only), and this Go
service's `internal/realtime`, `internal/embeddings` and `internal/synthesis` (below), all of
which need it **continuously** while the API process runs, not just for one command. Neither
ever writes the plaintext key to disk.

To run the API with realtime enabled locally, decrypt into this process's environment only,
same technique as the pipeline, then start the server in the same shell session:

```powershell
$secure = ConvertTo-SecureString -String (Get-Content -LiteralPath "$env:LOCALAPPDATA\Verbum\secrets\openai-key.dpapi" -Raw)
$bstr = [System.Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
$env:OPENAI_API_KEY = [System.Runtime.InteropServices.Marshal]::PtrToStringBSTR($bstr)
[System.Runtime.InteropServices.Marshal]::ZeroFreeBSTR($bstr)
go run ./cmd/api
```

Without `OPENAI_API_KEY` set, the server still starts and serves everything else normally;
`/v1/realtime/session` alone answers `503 realtime_unavailable`. There is no in-process way to
rotate the key without restarting the server.

## Realtime voice sessions

`POST /v1/realtime/session` mints one short-lived OpenAI Realtime API client secret
(`internal/realtime`) so a client app can connect **directly** to OpenAI (WebRTC/WebSocket) for
low-latency voice, without the real API key ever reaching the client. This was implemented ahead
of any client feature, at the owner's request, so the app side can be built later without a
backend change. Nothing about the resulting audio/voice session passes through this server —
it only ever makes the one small `POST https://api.openai.com/v1/realtime/client_secrets` call
per session request, and returns `{clientSecret, expiresAt, model}` with `Cache-Control:
no-store` (never cache or log this value). Not part of the read-only content contract (§45): it
doesn't touch `store.Store`. Owner still needs to build the client-side connection; this is
server-side plumbing only, and has not been exercised against a real client yet.
